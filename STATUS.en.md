On 2026-10-09 the external-plugin runtime pin was bound to the code that actually runs. `runtime_path` must cover the copy the runner will execute or import. For `python -m package.worker`, pin the package directory on that interpreter's import path, or the installation tree that contains the package. A direct script is pinned as the script file or the directory that contains it. Pinning only the interpreter, the wheel, or an unrelated copy is rejected at registration. Before execution, that copy's digest is recomputed; a changed digest or an entry that no longer lies inside the pin refuses to start. The plugin-copy version check now requires a PEP 440 version strictly greater than the baseline, so a downgrade or prerelease does not pass. The core remains `0.1.0a17` and the plugin source remains `1.0.2`. A deployed configuration that pinned the interpreter or an unrelated path no longer loads and must be registered again against the real installation tree.

On 2026-10-09 concurrency occupancy became the persisted `slot_held` mark, projected by the scheduler once per run id. If an approval result fails to persist, a later retry or restart still stores the approval outcome when the backend only reports that it is running, so the approval does not stay forwarding. Replaying a result and then restoring the scheduler counts that run once. A terminal run drops the mark, and public views omit it. An older row without the mark still follows whether the operation was dispatched and whether a release mark is present. On 2026-10-09 core result persistence and restart reconciliation were fixed. Multi-step result writes use one transaction. A failed write rolls back, the run becomes `pending_reconcile`, the operation becomes `unknown`, and the concurrency slot is released. The result stays in memory and is written onto the run when the state database accepts it. If that write also fails, later polls retry with a capped backoff until it lands, and the task is not dispatched again. A generic pending-reconcile update emitted after the worker stops does not replace that retained result. Foreground synchronous dispatch, confirmed cancellation, and approval replies use the same transaction. On restart, a run marked as released or missing its operation record does not take the slot back and is not executed again. A run that was still executing at shutdown and was not marked released keeps its budget reservation. A failed terminal checkpoint write rolls back the same way; restart replays the retained result, captures the checkpoint only after that write succeeds, and does not call the backend again.
