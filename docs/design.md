# Asterun 设计

[中文](design.md) | [English](en/design.md)

Asterun 在用户自己的电脑或服务器上执行 Agent 任务，统一管理配置、任务状态、原生会话、权限、调度和结果证据。CLI、MCP 和 GrokBot 等应用通过同一应用服务调用；核心可以独立安装和使用。

本文按 `0.1.0a13` 的实现整理。首版功能范围已冻结，后端支持和现场验证情况见[发行说明](release-v0.1.md)，接口细节见[协议实现表](protocol/IMPLEMENTATION.md)和 [capability profile](capability-profile.md)。

## 模块职责

| 模块 | 职责 |
|---|---|
| 入口适配 | 接收任务、建立调用主体、展示状态、转交审批和结果 |
| 通用核心 | 校验配置与授权，保存任务和会话绑定，安排执行，记录证据并处理恢复 |
| 后端适配器 | 调用原生协议，处理线程、轮次、事件、审批和终态 |
| 可选插件 | 在独立安装环境中提供已声明的能力，通过固定连接绑定账户与计费池 |
| 可选工作流 | 组织检查、独立审查、修复和复核，按固定输入版本给出验收结论 |

核心沿用 Python，在一个运行主机内由常驻执行器拥有执行权。CLI、stdio MCP 和同用户 Unix socket 共享应用逻辑；配置、会话、策略、状态库和证据分别组织为模块。接口版本与发布由 Asterun 管理，调用方应用负责自己的账户、模板和消息交付。

## 执行位置与账户

用户选择在哪台主机执行后端，就在该主机完成后端登录并配置工作区。GrokBot 可以调用其云电脑中的 Asterun，也可以通过已有授权通道调用用户本机的进程。调用方位置、Asterun 执行位置、账户和原生会话分别记录；跨主机传输由调用通道提供。

`model_provider` 表示模型来源，`execution_backend` 表示执行入口，`account_ref`、`runtime_ref` 和 `billing_pool_ref` 分别关联账户、运行主机和计费池。共用账户或计费池的入口按同一资源关系处理。凭据由原生工具或专用秘密存储持有，核心使用引用。

安装、登录、获权、实际调用、原生续接和客户端可见性各有验证状态。能力声明说明适配器接入范围，现场记录说明在指定版本与账户环境中验证了什么。

## 任务、会话与权限

`conversation_id` 关联业务会话，`task_id` 标识任务，每次尝试使用独立的 `run_id`。原生会话和轮次通过 `backend_session_id`、`backend_turn_id` 绑定账户、运行主机及工作区。重试沿用任务关系；原生线程是否复用由适配器能力和绑定检查决定。

调用主体由入口建立。每次执行前核对工作区、动作、授权期限、配置 revision 和后端能力。角色策略表达允许范围，原生权限模式决定后端如何执行，操作系统隔离另行配置。测试、构建和依赖安装按代码执行处理；同一范围内仍有效的授权可以复用。

Codex 保留 App Server 原生线程，并支持固定快照读取和可选桌面项目登记。Grok 的自主编码入口按工作区和命令范围执行。各后端的续接、审批和取消条件集中在[用户手册](user-manual.md)及对应后端文档。

## 状态、幂等与恢复

SQLite 是任务和控制记录的持久状态来源，当前版本为 schema 6。事件、产物和导出报告关联状态库中的记录。外部调用按“校验、提交操作意图、调用、记录结果”的顺序执行，等待后端期间释放数据库事务。

幂等键按接口约定限定主体、方法和目标。同键重试回读原操作，同键异输入返回冲突。请求可能已送达而结果不明时，先按原生引用对账；无法确认则保留未知状态和相关预算占位。

运行结束、任务验收和交付分别记录。取消先保存意图，再根据后端证据确认终止。人工接管先停止后续编排；恢复时重新核对最新轮次、输入版本、待批操作和目标变化。外部原生客户端的活动需要独立核实。

升级状态库前创建一致快照。回退使用与旧版本匹配的快照副本，同时保留新库供未决操作对账。备份范围和恢复步骤见[安装说明](install.md)。

## 工作流与资源

每个任务明确目标、资源范围、允许动作、输出、验证方法和预算，并指定一个 `orchestration_owner`。调用方编排时，核心执行提交的步骤；核心编排时，调用方提交目标、答复输入并观察结果。

代码质量流程按固定代码版本组织检查、独立审查、修复和复核。finding 与目标提交或文件哈希绑定；达到轮次或预算上限后交接当前结果。门禁结论、检查证据和发布状态分别返回，具体操作见 [PR 审查](pr-review.md)。

[外部主控工作流](caller-orchestration.md)用 `workflow.snapshot` 返回当前运行与所选文件的固定绑定。外部检查报告须匹配任务、运行、配置、输入、目标及报告字节；同次固定验收中的 `file_exists`、`file_contains` 路径也须包含在 `target_paths` 中。报告来源为 `external_reported`，不证明独立审查；`external_require_review` 持久记录已提出的审查要求，跨评价和修复保留，不能通过省略或改写后续请求绕过。修复在原任务新增运行、原子累计次数，保持完整版本绑定、幂等和既有上限；任务关系不等于原生会话续接。

可选插件使用固定执行计划。提交时再次核对输入、配置、插件安装、账户、权限和共享池，并在同一事务内记录预留与派发意图。用量保留原单位、来源和未知值，首版路由由显式配置选择。实现细节见[插件说明](plugins.md)。

观察器按有限时间窗口读取结果，宿主负责安排后续观察和聊天交付。收件箱消费者在宿主确认交付后写入回执，操作见[结果交付](review-consumer.md)。

`task.get compact` 与 `task-watch --compact --no-events` 保留状态、审批和续查引用，减少正文及事件搬运；默认行为不变，未读取的事件游标不前进。`usage.report` 只汇总已保存的原生用量，保留未知、部分报告与不可加总的累计范围，不请求供应商或证明实际扣款。部署与验证记录见 [STATUS](../STATUS.md)，真实使用效果和主控 token 净节省率另行计量。

## 维护与验证

默认检查使用临时目录和 fake 后端。真实后端、账户计费、原生客户端显示及人工接管按各自场景验证，结果记录固定提交、环境、命令和未验证项。

当前维护项见[开发规划](development-plan.md)，候选实验见[调优规划](tuning-plan.md)。早期取舍保存在 [ADR](adr/)，当前源码范围见[来源说明](source-provenance.md)。这些记录保留当时状态，当前使用以本页和操作手册为准。
