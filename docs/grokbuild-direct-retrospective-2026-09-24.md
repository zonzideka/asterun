# grokbuild 直调复盘与 Asterun 改进计划

日期：2026-09-24。来源是 jcssznzs 本轮开发记录，以及 Asterun 本地源码 84ec1655f187a4a5fff65222aa43df8f0edd150d。最初交付的是分析和计划；下方对照表保留复盘时状态，本轮实施状态见末尾记录。源码核对和离线验证不等于当前已部署二进制的现场验证。

## 本次实际差异

本轮早期 F01/F02 通过 Asterun 派发，后续改为直接运行 Grok Build 1.0.40、grok-4.7。两段任务规模和成熟度不同，不构成耗时、质量或费用的对照实验。当前 22/28 项隔离验收通过是整个开发过程的结果，不能全部归因于直调。

本地可核对的直调记录共 121 次尝试，涉及 26 个工作目录，引用 31 个原生会话。其中 92 次指定 --resume，82 次收到匹配该会话的 end 事件，75 次同时满足匹配会话、end_turn 和进程退出0；其余存在中断、回合上限或失败。正常退出不等于独立验收通过。按开始/结束时间计算，最高6个进程重叠；这是实际并发记录，不是推荐并发值，也不是吞吐提升比例。末尾三个进程都因402额度耗尽退出。

前期保留的5份 Asterun 派发响应对应 F01首次、两次修复及F02首次、一次修复，分别创建新 task。提交时 acceptance=pending、review_status=not_configured、repair_count=0。它们只是当时的派发快照，不代表现在的运行库仍是这些状态，也不证明 Asterun 缺少验收能力。本次接入没有充分使用已实现的 workflow.snapshot/evaluate/repair。

| 维度 | 本次直接调用 | 通过 Asterun 的现有能力与实际差异 |
|---|---|---|
| 原生特性 | 自定CLI参数、100回合上限、同原生会话续接；可以迅速适配当前CLI | 当前grok-code适配器每次新建UUID并传 --session-id，明确返回 native_resumed=false；同任务修复尚不等于原生续接 |
| 调度 | Codex拆分独立worktree、手动启动、停止、等待、组合 | 已有常驻执行、有界队列、按backend并发、工作区互斥；跨worktree依赖和验收后组合在本次仍由主控承担 |
| 反馈 | Codex把复现、报错和范围直接交给原会话，迭代路径短 | 已有固定外部报告和同任务有限修复；本次早期另建任务造成修复链分散，是接入方式问题 |
| 验收 | cleanenv和OS禁外联的脚本、临时PG、PHPWASM、实际Web合成浏览器；手工维护证据哈希 | 已有目标快照、检查前后版本核对、外部报告来源、独立review与失效逻辑；可以承接这些证据，无需再造质量系统 |
| 中断恢复 | PID、会话ID、NDJSON和WIP由临时脚本及Codex保存；402后人工逐树检查归档 | 持久任务、幂等、取消/未知状态和备份恢复是优势；Grok错误分类和代码检查点仍需补足 |
| 用量 | 文件散落各worktree，需要汇总、去重和解释原生计数 | 已有usage.report分页、累计口径及未知值保留；本轮直调没有统一写入任务用量链 |
| 工具权限 | 本次明确仅read/edit，终端和测试由Codex执行 | Asterun编码配置本身支持命令/测试。本轮编译返修不能归咎于Asterun必然禁止测试，两条路径都用了受限实施策略 |
| 诊断数据 | 直调wrapper直接落原始流，需要另行控制大小、访问和导出内容 | 现有适配器跳过thought、限制事件和字节、规范化公开结果；应保留这些治理能力 |

直调适合主控在线、单项目快速适配新CLI、需要立即续接修复的场景；代价是主控自己承担一部分调度器、状态库和交接工作。Asterun适合长任务、调用方离线、统一权限与账户池、多个入口共享任务、可恢复验收流程。Asterun不应成为限制原生能力的中间层，也不应把所有供应商细节交给调用方临时脚本处理。

## 优先级与交付项

以下保留 runner-control/v1、既有 task/run/acceptance、原生引用及未知状态语义。对首版冻结范围的缺陷和兼容性修复优先；工作图和直调接管等新增范围单独作为后续增量，不混进紧急修复。

| 编号 | 优先级／依赖 | 实现范围 | 交付与验收门 |
|---|---|---|---|
| A00 | P0／无 | 固定本轮脱敏事件和失败样例，补调用方范例，明确一个任务、多次run、外部验收、有限repair的正确接法；区分用户策略与后端能力 | 以fake CLI完整演示submit→snapshot→外部检查→evaluate失败→repair→复验；重复请求不增run，改目标后旧报告失效；不新建task规避修复上限 |
| A01 | P0／A00 | Grok原生续接：显式new/resume策略，按CLI版本及能力选择 --session-id 或 --resume；校验account/profile、runtime、workspace和会话绑定，串行化同会话轮次 | 同会话两轮、取消后续接、达到回合上限后续接、服务重启恢复、会话丢失、绑定错配均有fake回归；不支持时明确拒绝或请求显式新会话策略，不能静默丢上下文；原生现场验收等额度恢复后单独执行 |
| A02 | P0／A00 | 结构化识别402额度耗尽、429限流、认证失败、CLI回合上限、超时、协议截断；将供应商原因与本地已改文件/外部结果是否已知分开。接通Grok账户池停派 | 本轮“部分编辑后非JSON错误尾部402”作为回归样例；持久确认池耗尽后同池排队任务零新增派发，已在途任务有界收尾并保留证据；不把未知结果改成安全失败，不自动换账号、付费接口或充值；无官方余额证据时保持unknown |
| A03 | P0／A00，可与A01/A02并行 | 增加受控本地检查入口或复用已配置质量命令，让实施者拿到编译/局部测试结果；固定命令、cleanenv、无网络、超时、源码快照，不开放任意shell | 在G10/X01/X02脱敏样例中稳定发现语法、类型、fixture清单问题；有进程退出码、测试加载错误、pass/fail/skip、日志摘要和前后哈希；自测不能替代Codex独立验收。测试代码同样视为可执行代码并隔离 |
| A04 | P1／A01+A02+A03 | 自动生成可恢复检查点，绑定task/run/native session、基线HEAD、dirty文件清单/哈希、私有补丁、新增文件、最后诊断和下一动作；缩短常态观察输出 | 注入终态落库前崩溃、日志截断、磁盘写入失败、取消竞争、调用方退出，恢复后不重派已送达工作；恢复前校验源树漂移。默认保存产物而非自动git提交，更不能暂存用户原有dirty文件；独占授权worker可显式启用WIP提交 |
| A05 | P1／A00+A04 | 将“编码检查通过、消费者接线通过、独立审查通过、组合后通过、已部署”作为分离证据，接入现有workflow和compact观察；失败诊断按文件/错误类别压缩 | 单测全绿但路由未接线、12个测试文件加载失败却failedTests=0、源码变化后沿用报告等样例均不能验收；报告绑定commit/文件快照与环境，缺项保持未验；external_reported不得冒充独立审查 |
| A06 | P2／A02+A04+A05 | 在既有scheduler和billing pool之上加项目依赖、独立worktree分配与组合队列；实施并发与本地验收并发分别限额 | 先使用3路实施/2路检查作为可配置实验值，而非宣称最优；同一工作树单写者，依赖验收前不放行，两个worker均绿但组合失败时不标项目完成；额度熔断后不继续启动新依赖任务 |
| A07 | P2／A01+A04+A05 | 可选直调记录导入和原生会话接管，复用现有原生日志同步的安全校验；历史导入先只读，明确 external_observed 来源 | 首次导入和重复导入不重复计量、不执行模型；active PID、绑定不明、路径逃逸和内容漂移拒绝接管；只有确认旧执行方退出、取得单一执行权后才允许resume；不把历史进程exit0导入成accepted |
| A08 | P2／A01—A05 | 扩展已有tuning-plan度量，比较“直调／当前Asterun／改进Asterun”在同一任务集下的完整验收过程 | 先fake协议对照，后在明确额度预算内做6—10项小样本；固定代码基线、模型/CLI、工具权限、上下文策略、并发和质量门。分别记录主控/实施用量、返修、读取字节、等待、人工介入、完成时间和质量；无对照数据不发布节省百分比 |

首个交付批次为 A00—A03：正确使用现有工作流、原生续接、额度停派和及时编译反馈。第二批 A04—A05 减少手工收尾并防止错版本验收。第三批再考虑项目并发编排、直调接管和实测调优。每批均需CLI与MCP入口、进程重启恢复和旧配置兼容测试；部署与真实模型验收另列，不因离线通过而自动切换实例。

A03优先回传局部编译与相关测试；全量检查放在稳定检查点和集成候选。失败重复出现但文件未变时复用诊断，不反复运行同一全量套件。新增诊断应先归因是实现错误、夹具失真还是检查器假设错误，再进入修复。权限、原生字段、资源身份等问题仍需要消费者审查，不能指望多跑编译解决。

A01复用会话也有代价：旧假设会延续，长上下文可能增长。每轮只附增量诊断和当前目标快照；发生架构切换、依赖变更或连续无进展时先保留会话记录，再按明确策略新建会话。禁止把无限resume当成预算管理。A02应保留用于验证和保存检查点的本地资源余量；没有可靠供应商额度接口时，只能基于实际错误、用户给定预算和有界尝试控制，不能估算一个伪精确余额。

## 2026-09-24 继续实施记录

本轮补齐 A03 的后台检查与可选诊断缓存，并交付 A04/A05 的首个可用范围。异步检查复用现有运行持久记录和执行器，限定两个检查槽位；客户端退出后继续落盘，同键不重复执行，重启未决保留 unknown。运行时无法在限额内完整指纹化就禁用缓存；成功、失败可复用，超时、取消和未知不复用。缓存只覆盖同运行、同完整绑定，不宣称跨项目或跨运行命中率。

A04 按显式 checkpoint_paths 保存选定文件：派发前记录当前脏基线，终态前保存内容、模式、新文件与文本差异。私有产物存入已有 SQLite blob 表，随状态备份恢复；CLI/MCP 查询检查源码漂移、身份和下一动作，不自动写回、提交或续接。当前不是整棵工作树备份，也不是实时连续保存：硬崩溃时可能只有基线，用户须先处理漂移和对账。原生日志损坏沿用 A01 拒绝续接。未实现自动 WIP 提交。

A05 通过检查配置 stage 和 workflow.evidence 分开展示编码、消费者、独立审查、组合、部署状态。失败按文件/类别压缩；单测绿不代表消费者已接通，加载失败不当成零失败，源码或命令漂移不复用旧结论。独立审查只接受既有核心质量流程绑定，fake 标 simulated，外部自报保持来源。部署证据接入和可配置跨阶段 acceptance 门禁仍待后续，当前显式报告未验；现有 evaluate 的检查列表仍由调用方完整提供。A06—A08 未启动，未增加真实模型调用或部署切换。
